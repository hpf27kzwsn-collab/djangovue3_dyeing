# 订单、染整报价与生产模块只读核查

核查日期：2026-10-22。直接连接 localhost / Textile_GXHFRS，Windows身份验证。旧数据库仅执行SELECT；没有修改代码、菜单、模型或导入任何数据。统计包含当前旧库全部记录，不按启用、常用或异常状态排除。

## 一、染整订单与加工订单是否应分成两个模型

**结论：染整订单应作为主要业务入口；现有证据不支持直接另建一套名为“加工订单”的销售订单模型。业务入口、订单类别和数据库模型不能混为一件事。**

旧功能010200“染整订单”对应F_OrderList，其MasterDataTableName为OrderMain；010201“订单新增”对应F_OrderEdit。旧s_UINav也明确把010200显示为“染整订单”。本轮查询旧功能名称、导航别名及相关表单配置，没有发现独立名为“加工订单”的销售业务入口或第二套对应主从结构。

|旧表|全部记录数|实际作用|
|---|---:|---|
|dye.OrderMain|17,032|原销售订单表头，主要染整订单入口的来源|
|dye.OrderColor|80,053|原订单颜色明细|
|dye.OrderProcess|0|原订单工序表，不能因空表删除其定义|
|dye.OrderInfo|0|另一份原订单信息结构；不能仅凭存在此表认定它就是加工订单|
|dye.OrderInfoProcess|0|上述结构的工序资料|

OrderMain全部记录分布如下：

|SheetKind|SheetType|BusinessKind|OrderKindID|记录数|
|---:|---:|---|---|---:|
|1|10|NULL|NULL|13,133|
|2|10|NULL|NULL|3,899|

旧字段配置把SheetKind交给程序枚举TF.Enum.EnumFactory+TOrderSheetKind，SheetType交给TOrderSheetType。本轮数据库配置没有给出1、2的可证明中文名称，不将这两个数字自行解释成“染整/加工”。p_FieldValid.OrderKind虽有坯布加工、色布加工、客退回修、销售订单四项，但实际OrderKindID全为NULL，也不能据此把17,032张历史单据分入四类。

另外，旧系统有独立印花订单功能和PrintOrderMain界面，但PrintOrderMain仍写OrderMain，查询限定SheetKind=40。本库现有OrderMain未出现40；空数据与停用/少用功能仍保留。此例直接说明：独立业务入口不必对应独立物理主表。

新系统目前同时存在：

- SalesOrder：此前新增的整理模型，模型名称为“加工销售订单”。它不是从旧库证明出的第二套“加工订单”原表。
- SourceDyeOrderMain及其明细模型：对应旧原表、原主键和原字段的复刻模型。

因此，当前名称及并列入口容易误导。后续应把原OrderMain业务明确呈现为“染整订单”，将原正常、重修、改染、试样、印花等业务按证据配置对应入口/类型；不能把整理模型与原表模型当成旧系统的两种订单。若“加工订单”特指松筒、加捻、翻松等受托加工，须依据它们原订单/工卡的实际来源定义业务入口，不能只凭名称新增第二套销售表。本次未擅自作此业务定义。

## 二、是否已有大量染整报价，导入包是否已提供

**结论：有真实染整报价；此前基础资料xlsx包没有提供这些报价本体。**

旧功能010101“染整报价新增”打开F_QuoteEdit。其逻辑数据集虽叫Quote，但s_DataTable明确将Quote绑定FixedPrice、QuoteDetail绑定FixedPriceDetail；旧Quote列表查询和QuotePriceList报价查询也实际读取FixedPrice、FixedPriceDetail。不能只按相似表名读取dye.Quote并判定没有报价。

|旧表|全部记录数|说明|
|---|---:|---|
|dye.FixedPrice|20|报价表头，涉及13个非NULL客户编码|
|dye.FixedPriceDetail|847|报价明细，关联上述20张表头，303个不同非NULLProdID；无缺失表头明细|
|dye.Quote|0|另一个同名原物理表，不是当前染整报价录入的实际写入表|
|dye.QuoteDetail|0|另一个原明细表，不能替代FixedPriceDetail|
|dye.CusAddPrice / CusAddPriceDetail|0 / 0|客户加工单价原表仍保留|
|dye.ZDAddPrice / ZDAddPriceDetail|0 / 0|织带加工单价原表仍保留|

847条明细的价格字段不能混用：

|字段|旧界面含义/配置|实际情况|
|---|---|---|
|CusPrice|QuoteDetail中的“对客报价”|837条非NULL、非零；10条NULL|
|Price|QuoteDetail中的“客确价格”|847条均NULL，不能因此判定所有报价为空|
|Pricesum|QuoteDetail中的“总单价”|847条均为0，不能拿它覆盖CusPrice|
|ConPrice / StanPrice / ProcessPrice / RecipePrice|参考价/标准价/工序价/配方成本等各自原字段|本批上述字段均NULL，保留原状态|

QuotePriceList和QuoteDetail的字段标题、表达式还存在差别，例如列表Price标题为染整单价，编辑界面Price标题为客确价格。承接时须保留具体入口与原字段，不能按标题相近擅自合并或重算。本轮只统计，未导出报价明细或改变原值。

已逐项核对20261021导入包的文件校验目录、表级资料统计和实际文件目录：

- 没有FixedPrice、FixedPriceDetail的已有数据文件或新增模板；所以20张报价、847条明细尚未通过该包交付。
- 已有报价类别及客户、物料等配套资料；小缸价格p_PriceList有6行，工序价格明细p_PriceListProcess有9行，色深价格明细p_PriceListColor有8行。这些不能代替本批客户染整报价。
- 导入包表级统计也不包含s_DBComboValue。报价的C010计价单位、Z010服务方式不能笼统声称已经作为该xlsx包交付。旧库C010有元/吨、元/kg、元/缸、元/米、元/条、元/码；Z010值“本厂采购”显示“包工包料”，“客户来纱”显示“来料加工”。后续应和报价主从资料一并明确提供，保留保存值与显示值的差别。

新系统已定义SourceDyeFixedPrice、SourceDyeFixedPriceDetail及原Quote录入绑定；这不等于已经交付或正式导入数据。两模型仍显示为“财务结算与成本相关表（待确认）”的旧分类标题不准确，应按销售报价更正。source_catalog实际handling为business_model，reason为“报价/订单/客户业务来源”；本轮没有证据表明它们在代码中被整体当财务功能禁用，不把不准确标题说成已经删除了报价。

后续应在销售管理明确提供“染整报价/客户价格档案”，单独整理20张表头及847条明细和关联配套资料。10条空对客价、零总单价及历史状态均原样保留，不筛掉。报价属于销售业务，不能随财务暂缓。

## 三、生产管理是否拆成工艺设计、排产管理、生产管理

**结论：建议按这三种业务职责拆分前端模块与办理入口；旧系统本来就有技术、计划、执行的划分。但不是旧ERP恰好存在同名三个模块，也不意味着立即重建三套数据库。**

旧s_Module分别登记了工卡管理（3）、计划管理（4）、染色技术管理（21）、工艺参数管理（22）、车间管理（12）、刷卡程序（60）。以下为按旧功能定义统计的入口数量，含目录、查询、新增及动作，不能理解为独立模型数：

|旧模块|功能定义数|IsEnable=True|说明|
|---|---:|---:|---|
|工卡管理|94|50|转卡、染整/松筒/加捻/销售工卡、工卡处理等|
|计划管理|29|6|含旧排产与新染色排产、装缸排产查询等|
|染色技术管理|63|17|含来样/打样及配方，不能整块直接搬出打样模块|
|工艺参数管理|12|0|11项False、1项NULL；技术定义仍保留|
|车间管理|97|34|产量、现场录入、返修及生产统计等|
|刷卡程序|33|32|站别/工序/机台选择、报工与现场处理等|

本库实际存在：DyeRecipe 65,678行，DyeRecipeDetail 541,217行，ProcessSchedule 139行，JobSheet 92,538行，WProcess 389,052行，RecordYield 377,215行。数字是各表物理行数，不互相相加成“生产单据数”。ProcessScheduleRS“新染色排产”逻辑数据集实际写ProcessSchedule，不应再造一份同义排产表。

建议职责如下：

|新模块|主要业务职责|与其他模块的边界|
|---|---|---|
|工艺设计|标准/量产工艺、工艺路线、工序技术参数、标准/生产配方、工艺确认与版本|来样、试样任务、打样过程及其试验配方仍保留打样职责；引用关系共享，不能复制成互不相干两份|
|排产管理|订单转卡准备、工卡拆合/分缸、机台/缸号安排、工序计划、生产顺序、改排、交期协调|工卡同时是后续执行依据；模型保留一份，主办入口及跨模块查看明确区分|
|生产管理|现场领料/称料办理、工序开完工、刷卡/补录、人员机台实际投入、产量、返修/再加工执行|仓储保留实际收发、库存及包装出入库职责；质量检验与处置仍归质量管理；设备通讯配置仍归系统管理|

当前配方集中在打样管理、RecordYield产量来源在仓储管理、ProcessSchedule仍使用含糊工艺类标题，均说明需要按职责整理。后续先建立旧功能→新模块→原模型→服务→前端入口的归属表，再改菜单和页面；复用原模型、主键、服务及完整关系，不为改菜单立即搬Django app或复制原表。启用、停用、空表、异常及重复业务均列入对应归属，不因拆分跳过。

## 本轮边界

本轮是旧库事实核查与架构判断；不是实施上述调整、报价包导出、数据正式导入、历史全量对账或现场验收。财务、打印及原35项查询仍按既定范围暂缓，额外旧erpID仍不增加。
