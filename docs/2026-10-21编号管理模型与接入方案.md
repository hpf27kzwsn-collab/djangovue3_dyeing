# 编号管理模型与接入方案

日期：2026-10-21。当前状态：编号管理、29条建议规则及独立库/浏览器验证已实施；已引用资料改码与复杂单号变更仍有限制。详见[实施与验证](2026-10-21编号管理实施与验证.md)及[异常事项](2026-10-21编号管理异常与后续事项.md)。正式旧资料导入数量为0。

## 设计结论

新增“编号管理”模型，让使用人选择已有业务模型、编码字段和业务范围，设置固定前缀、流水位数，以及是否允许手工录入和修改编号。生成方式只做“固定前缀＋补零流水号”，例如HF1687、G094、A014。

先按已有原编码初始化29条建议规则。日期单号、父单明细号、原自增主键、设备条码、带固定业务含义的代码继续采用其对应方式，不强行套成普通流水号。它们的基础资料、单据及异常原行仍完整保留和支持录入。

新管理器绑定已有字段，不给所有模型追加一列Code，不增加旧erpID。新系统的id、旧表原有主键、原有业务编码继续分别保存。

本方案承接[基础资料编码与自动编号核查](2026-10-21基础资料编码与自动编号核查.md)。基础资料编码样式来自2026-10-21只读提取，业务单据示例来自2026-10-14完整业务快照；新规则建议基于这些证据，不代表已经读取正式使用库的当前最大号。

## 使用界面

入口放在“管理设置 → 编号管理”。前台使用部门、员工、客户、采购单等业务名称，不展示技术模型名作为主要操作名称，也不增加“复刻系统”等产品文案。

新增规则按以下顺序填写：

1. 选择模型，例如客户/供应商原形资料、业务员工、机物料。
2. 选择该模型现有的业务编码字段。多编号模型分别列出字段含义，例如机台编码与机台编号；不混为一个字段。
3. 选择业务范围，例如客户、供应商、后纺包装、某机物料类别。范围由已有资料分类和明确登记的分组提供，不要求使用人写SQL或表达式。
4. 设置前缀、流水位数和起始流水号；可查看样式及已有号码基线。
5. 设置“自动生成编号”“允许手工录入”“允许更改编号”。

选择日期单号、固定含义代码或尚未有改码适配的对象时，界面说明现有处理方式和可操作范围，不显示一个实际上不起作用的开关。

## 编号管理模型字段

建议模型为erp_base.NumberingRule，中文名“编号管理”，沿用项目ErpModel的id、创建人、修改人、时间和业务备注等公共字段。

| 字段 | 建议类型 | 含义和处理 |
| --- | --- | --- |
| name | CharField(100) | 规则名称，如员工编码、供应商编码 |
| target_model | CharField(100) | 当前模型标识，通过模型下拉选择，不自由输入 |
| target_field | CharField(100) | 已有编码字段，如old_emp_id、old_customer_id |
| scope_key | CharField(200) | 登记的业务范围，如客户、包装分类或明确的业务入口 |
| scope_filters | JSONField | 后台生成的固定等值/包含条件，如CustKindID=1；前台不编辑JSON |
| entry_name | CharField(100)，允许空 | 只有范围确实依赖业务入口时填写，不代替资料自身类别 |
| prefix | CharField(64)，允许空文本 | 固定前缀，如HF、G、PD-；空前缀表示纯数字 |
| digits | PositiveSmallIntegerField | 数字部分位数，建议1～18位，并受原字段总长度限制 |
| start_number | PositiveBigIntegerField，默认1 | 空号码池起始值；允许0，支持旧客户000这类编号 |
| last_number | PositiveBigIntegerField，允许NULL | 已接续的流水基线，只由服务维护；NULL表示尚无基线号码 |
| auto_enabled | BooleanField，默认True | 是否自动生成编号 |
| allow_manual_input | BooleanField，默认True | 普通新增是否允许明确输入编码，包含Excel新增 |
| allow_code_change | BooleanField，默认False | 已有记录是否开放更改编号；仍需走该模型的改码服务 |
| notes | TextField，允许空 | 说明适用范围、原样式和已知差异 |

业务唯一配置键为“模型＋编码字段＋范围标识”。一个新记录的同一编码字段只能匹配一条规则；全模型规则与分类规则重叠时不能同时接管同一记录，不按配置顺序猜测。

第一版目标字段限定为已有、可写的文本业务编码字段。数据库自增、外键id、UUID、计算属性和外部来源标识不作为普通前缀流水字段。没有合适字段的模型不擅自新增编码列。

“自动生成编号”关闭后，已接管范围改为手工编号，不能又偷偷调用旧自动号。此时应允许手工录入，否则该配置没有可用的新建方式。尚未配置新规则的范围继续采用原入口方式。

## 简单编号的含义

公式为：固定前缀＋按指定位数在左侧补0的流水值。

| 前缀 | 位数 | 流水值 | 生成结果 |
| --- | ---: | ---: | --- |
| HF | 4 | 1687 | HF1687 |
| G | 3 | 94 | G094 |
| 空 | 3 | 19 | 019 |
| PD- | 3 | 227 | PD-227 |

位数只指数字部分，不包括前缀。不能再出现“配置4位，实际强制生成6位”的情况。达到999等位数上限时明确提示号码位数已满，不截断、不回到001，也不擅自扩大位数。

生成结果必须装得进原字段长度。大整数基线在前端和接口使用十进制文本传递，避免JavaScript的数字精度改变流水值。

前缀和位数约束自动生成的号码，不强迫合法的手工码或历史原码符合新格式。允许手填时，不给这些原字段新增额外的统一格式约束。

## 业务范围与号码池

“哪条记录使用本规则”与“号码在哪个范围不重复”要分别确定，但前台不需要配置一套通用条件语言。

| 对象 | 规则匹配范围 | 号码池处理 |
| --- | --- | --- |
| 客户与供应商 | p_Customer的CustKindID=0/1 | 两条规则，分别数字前缀与G前缀；不把G001转整数后混入客户取号 |
| 包装、纸筒、销售区域 | p_FieldValid的FieldType分类 | 原键含FieldType，分类内各自接续；快捷入口不重复建池 |
| 幅宽、克重 | WidthGramWeight.Code | 原Code是共表主键，两类共用一条规则和一个流水，不能各自生成019 |
| A系列染化料 | StuffKindID属于FS/HX/SX | 三个类别合用一个A系列流水，不能各类分别从A001开始 |
| W/Z系列染化料 | 对应ZJ/GY | 分别W、Z前缀；保留全部原类别和原编码 |
| 机物料 | 明确的ArticleKindID类别 | ArticleID为全表身份，同前缀原码在全表核对基线，不能因旧物料分类变更而撞号 |
| 单据的可显示编号 | 实际单据模型及明确业务类型 | 不拿共享模型名代替业务类型；原复杂单号不默认接管 |

范围只支持已有字段的等值或明确的值集合，按原字段保存，不改原值。数据库中存对应的新模型字段名；下方表格为方便阅读使用旧字段名。

范围、前缀和撞号比较沿用该原字段已确认的大小写及尾随空格语义，内部比较不改写原字符串。例如旧字段不区分大小写时，手填g999也应进入G系列的基线核对，不能让新自动号与它冲突。

原唯一范围通过逐模型的编号适配登记，不能单凭某个字段叫Code就猜。跨范围可能生成同一号的规则不能并行启用：应共用一条规则或采用不重叠的编号格式。

第一版不加“遇到多条规则就取第一条”或“自动选择最多人用的前缀”。同一类别有多系列且无法根据已有字段唯一选择时，保留手工录入与原有方式，列出其样式，不删除少数系列。

- 客户只消费一次CustomerID流水，Num按原默认关联生成K＋CustomerID；供应商新号写入CustomerID并按原关联写Num。不能两个字段独立取号，也不能被旧的[NUM]公式重新覆盖为空。显式手工输入按原入口优先级办理；历史两字段不同的记录仍原样留档。

## 业务单据的接入

本项目既有基础资料也有不同业务单据。新增编号管理不是把所有SheetNo直接改成一个固定前缀；需要区分独立单号、含日期单号、继承编号和明细编号。

当前入口配置中有214项SheetNo编号定义，其中207项为DateCode、3项FollowSeries、2项AutoAdd_Local、1项AutoAdd_Time、1项SeriesAndRowNo。它们是入口配置项数，不是214张表，也不是本轮启用数量。财务身份仍按实际用途排除，例如商业发票相关入口，不只信任旧分类标记。

| 业务 | 旧单号示例或规则 | 默认接入方式 |
| --- | --- | --- |
| 销售订单OrderMain | K#240902002等，含日期与业务前缀 | 保留原日期规则，不改成K#000000001 |
| 采购单PurMain | H240910001等 | 保留原日期及业务范围 |
| 工卡JobSheet | 240902F0201等，含日期及机台/生产身份结构 | 保留专用生成及关联，不按最大数字简单加1 |
| 成品入库、出库 | 240910001、240913001等 | 保留日期号及原库存事件时机 |
| 打样、配方 | 配方201706110001等；标准/试产部分入口跟随来源号 | 保留日期或来源继承，不再独立发一遍来源编号 |
| 报工、质量、包装、交付及其逆向链 | 可能包含工卡号、卷/箱序号、内部GUID及实际标签 | 显示单号、来源码和条码分别处理，不改变原来源链或重复标签含义 |
| 工卡接收、工卡登记等 | SheetNo实际上引用工卡，并非该表自己的独立单号 | 跟随来源，不为每条接收记录重发工卡号 |
| 员工异动、奖惩 | 配置有普通本地流水，但2026-10-14快照各0行 | 属于可配置候选，不预设已有数据起点；若采用需明确绑定字段后验证 |

因此第一批29条建议均为有实际编码证据的基础资料规则；不会为了增加业务单据接入数量而把日期号改成普通流水。业务单据在管理界面可展示其编号方式；确需改用固定前缀流水时，按明确的新规则接管该显示字段，并登记这是新规则选择，不冒充旧日期规则已原样复刻。

对于旧日期规则本身已有的超长、字段对应或生成时机问题，仍应单独按原逻辑修复；不能把“本次不套简单规则”当作不处理这些差异。

## 保存与服务层调用

编号逻辑集中到编号服务，不放在Vue、Serializer.save内部、模型save信号或数据库通用触发器里。基础资料新增、业务单据新增、Excel新增、转单和后台自动建单共同调用同一入口。

处理顺序如下：

1. 明确真实模型、业务入口、资料类别及父单来源，应用必要的类别默认值。
2. 判断是否为历史原值承接。历史方式保留原码和原主键，不生成新号，不受普通新增手填开关阻挡。
3. 对普通新增确定本字段是否由编号管理接管；没有接管的范围继续现有方式。
4. 根据规则决定手填或自动生成，取号与最终保存放在同一事务中。
5. 生成依赖字段、保存明细和业务事件。已接管字段不再被旧编号、旧公式重复取号或覆盖；其他默认值、日期、人员和非编号公式继续执行。
6. 保存失败时整体回滚，包括流水更新；预览和打开新增表单均不占号。

第一版直接锁定编号管理记录维护last_number，不另建一套计数器模型。SourceIdentitySequence仍服务于未接管的旧规则和原自增字段，不能全库清空或与新规则对同一字段重复发号。

需要调整的现有调用处包括source_entry_services/source_numbers、source_services、source_phase6_local_values中的客户供应商联动、旧转单和自动建单服务，以及source_excel的日常新增路径。整理模型的code/number也可接入同一服务，但没有明确采用关系时不照抄一套原形资料规则，避免同一业务产生两套相互独立的编码。

## 编号基线和历史导入

建议配置页提供“查看原码分布”“同步流水基线”“预览新样式”。取号按数值尾号比较，不对完整字符串做字典序MAX。

1. 按已明确的号码池范围读取全部存量编码，识别本固定前缀后的数字尾号。
2. 原号码尾号长度不同仍参与数值基线核对，不因新规则3位就漏掉旧2位数字码；原字符串不改写。
3. 不属于本系列的前缀、NULL、空文本和其他样式分别列出并保留。它们不参与本系列的数值运算，不表示导入时被跳过。
4. last_number取已知存量尾号最大值、已有新规则流水及能明确对应的旧计数器已用值的高值，绝不回退。无法对应的旧序列保留并列出映射事项，不删除。
5. 既无基线也没发过号时使用start_number；否则使用不低于start_number的下一个流水值。
6. 手工录入本系列号码时同步抬高流水；手工录入其他合法样式不擅自改码。历史承接也在完成后同步相关基线，不调用新号生成。所有写入该字段的路径都要通知对应号码池，包括未接管分类里的手填和旧服务写码，不能只在新管理器自动发号时同步。

初始规则和历史导入并发时，受影响的规则应在导入事务开始时按固定顺序锁定，完成原码保存和基线同步后释放；其他新增也锁同一规则。对于原来全表共享的身份字段，其他分类手填同系列号也使用对应号码池的锁和同步；原复合键分类可以分别发号。多编号字段按固定顺序取号，避免两条规则互相等待。

不在保留异常/重复原值的旧表上强加全局编码唯一约束。自动发号不产生新冲突；手工码按原模型已有业务约束处理；历史重复仍完整导入并登记，不能按编码去重或覆盖。

成功保存后发生业务撤销、删除或跨链逆向，不回退已经发出的流水；号码计数不加入业务链的反向还原清单。只有最初保存事务失败才回滚本次取号。

前缀、位数或起始值变更只影响后续新号，不重编号已有资料，也不自动清零流水。已使用规则不把目标模型、字段或范围改成另一种资料；另行建立明确配置。关闭自动生成后保留基线。

## 手工录入与更改编号

“允许手工录入”和“允许更改编号”必须分开。初始29条规则建议前者开启、后者关闭，这既能按旧码导入，也避免误把资料改码当普通文字编辑。

| 场景 | 处理 |
| --- | --- |
| 允许手填，输入了编码 | 使用明确输入值，不再自动重编 |
| 不允许手填，输入了编码 | 明确提示该范围使用自动编号，页面/接口/Excel一致；不能借Num等别名绕过 |
| 自动开启且真正未填写编码 | 调用编号服务生成 |
| 自动关闭且允许手填 | 要求填写编码；不能又回退旧自动号 |
| 历史原值承接 | 原码照存，不按“禁止手填”拒绝，也不重放编号事件 |
| 未允许改码，实际编码变化 | 不接受该次改码；其他字段仍可按原业务办理 |
| 提交的编码与原值相同 | 不是改码，不再出现仅因为提交了编码列就报“不能修改”的情况 |
| 允许改码 | 走对应模型的明确改码服务，不能只改主表字符串 |

页面原有“使用自动编号和默认值”应拆出由编号规则决定的编号控制，不能继续让它绕过服务层开关。其他默认值的选择保留其原用途。Excel留白、#NULL、#EMPTY的语义不能混为一谈；历史空值仍按原值方式承接。

改码需要特别处理：

- 新系统id不变，不重建记录；原系统自带主键/业务码若是修改对象，记录改前和改后值，不新增旧erpID。
- 尚无引用的资料、未流转单据可以在对应服务中直接改码并记录现有业务日志。
- 已有FK和旧字符串码引用的资料，只有登记并验证了完整引用处理的模型才开放改码。引用通过实际新记录id/明确原关系确定，不按一个可能重复的旧码批量替换所有记录。
- 历史单据中的成交快照、来源号、条码和库存事实不能因主档改码被整库重写。凡旧服务仍依赖字符串关联的链条，必须提供明确的关系更新/改码适配；缺少适配的模型先不开放修改开关，并列入改码待接入清单，原数据与录入能力不减少。
- 已流转或已产生库存、质量、包装效果的单据，不能靠勾选允许改码绕过原有更正/撤销流程；不额外发明统一草稿、确认、审核阶段。
- 历史原键改变后，对账应通过已有批次、来源行和改码日志辨明原号与现号，不把人为改码误报成漏导，也不修改原始xlsx/来源文件来伪造一致。

因此“允许改码”是编号层允许进入改码办理，不等于所有历史引用都可以随意改写。实现时必须在可用性清单中明确哪些模型已支持无引用改码、哪些已支持关联改码，不能只加一个布尔字段就标记全部完成。

## 前后端与权限调整

编号管理列表展示模型、字段、范围、前缀、位数、当前流水、三个操作开关和样式示例。模型选择后只提供对应业务编码字段；同一来源的快捷菜单共用规则。

普通资料新增表单显示“自动生成”或编码输入框，编辑表单按实际改码能力显示操作。客户和供应商使用各自中文编码标签，底层仍对应旧共表字段。不要让用户为了编号理解_source_model等实现名。

规则维护、基线同步和改码办理沿用项目权限机制；规则修改、基线同步和手工改码沿用BusinessAction记录。普通单据新增日志保留最终编号，不为号码管理再创造一个业务入口或重复执行保存事件。

编号管理的普通页面操作提示只解释本规则影响范围和实际失败原因，不加入未经请求的额外审批流程。

## 开发顺序

1. 固定编号目标登记：明确原字段、资料范围、号码池、固定含义代码及不接管对象，保存29条建议和全量来源去向。
2. 新建NumberingRule、迁移、查询与维护接口，以及模型/字段/范围选择。只增加该管理模型，不改现有资料原字段类型和历史值。
3. 实现简单编号与基线服务：固定前缀、严格位数、手工控制、事务锁、失败回滚及基线同步。
4. 接入基础资料保存和Excel新增；解决客户/供应商双字段联动、员工位数、部门DateCode超长及共表分类串号问题。
5. 接入转单和自动建单的公共编号调用，验证日期、继承、明细和内部身份继续按原方式办理；不因接入增加重复单号或改变来源。
6. 实现编号管理页面、录入表单及可用的改码服务；逐模型登记引用处理能力，暂未实现的改码链明确列项。
7. 在独立验证库完成编号、导入和业务回归，以及浏览器新增/编辑/Excel操作，再更新基础资料新增模板中的编号说明。
8. 更新开发清单、编号差异及改码待接入文档，分别记录开发验证、历史对账和现场验收状态。正式旧资料导入仍由使用人操作，不自动代导。

## 注意事项和实现边界

- 财务系统、打印及原35项查询继续暂缓，不把科目码、发票号或打印标签任务混入本批自动规则初始化。
- 工序GX99、分段步骤及日期色号的例子说明：样式看起来像“前缀＋数字”并不足以证明适合普通流水。初始化必须同时看字段业务含义与调用关系。
- 需要做的检查限定于编号规则本身、原字段长度、业务范围、发号一致性和已知引用关系，不堆叠无关的防御分支。
- 不吞异常后换另一生成器，不把原字母码转0，不截断溢出，不自动改前缀，不从第一个同名模型或范围猜规则。
- 自动规则不合适的来源继续完整录入；改码暂未适配的来源继续保存和使用，不以功能差异删除或跳过数据。
- 新模型仅是编号配置管理，不自动采用整理主档，不自动正式导入旧ERP，不改变全部业务流程或单据状态。
