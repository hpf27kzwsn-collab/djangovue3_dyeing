# 客户独立使用ERP与过度编码整改方案

日期：2026-10-24。性质：整改方案及原完成标准；本轮代码实施结果见[实施清单与验证](2026-10-24客户独立使用ERP整改实施清单与验证.md)。本方案优先于之前“保留开发核验在管理员维护入口”“先完成全历史对账再使用”的安排。

## 1. 产品目标和开发边界

本系统交付给客户实际生产使用。客户在新系统中自行导入基础资料、录入业务单据，完成销售、采购、打样、工艺、排产、生产、仓储和质量业务。前端、后端、初始化和部署都围绕这些职责设计。

旧ERP数据库是开发参考：用来理解字段、关联、计算、业务流程和少见分支。读取旧库、提取快照、逐字段比较和复刻覆盖统计是开发工作，不是客户使用系统的组成部分。不能将“参考旧库”解释成建设长期新旧并行、在线同步、旧数据自动采用或客户自证复刻的平台。

具体约束：

- 客户运行新系统不需要旧SQL Server，不需要旧数据库连接信息，也不需要开发电脑上的旧导出目录、JSONL、索引文件或开发核验清单。
- 报价关联订单、工卡关联订单、收发关联生产等，全部关联客户已经导入或录入到**新系统本地数据库**的记录。旧表原字段/编码可继续用于本地业务关系，不等于跨库引用。
- 客户可以从空业务库开始导入资料、录入新单；不能要求先注册旧库快照、完成旧新映射、导入一批旧单、运行核对命令或打开核验页面。
- 前端只展示客户可理解的业务及必要管理功能。后端不因按钮隐藏就继续默认注册无关API、权限和任务。
- 真实业务需要的计算、引用检查、单位处理、事务、库存和逆向保留。禁止无依据的通用审批、猜测关系、静默兜底、自动清洗及新造通用执行平台。
- 停用、不常用、异常和重复业务不能按频率或数据外观删去；旧平台自身的窗体/菜单/收藏/权限机制不因此成为新产品必须复刻的业务。
- 财务、打印和原35项查询继续暂缓；不新增【旧erpID】，不擅自正式导入或清理数据。

## 2. 对当前代码的核实结论

### 2.1 是否直接引用旧SQL Server

**在本轮检查的默认应用配置及运行代码中，没有发现日常后端直接连接旧SQL Server的实现。**

- [settings.py](../backend/application/settings.py#L27)只有一个默认Django数据库配置；[database_config.py](../backend/application/database_config.py#L18)实现的是SQLite/PostgreSQL配置，没有MSSQL数据库别名或旧库路由。
- `source_phase6_entries.reader`通过Django模型读取新库；`source_static_lookup`把登记的旧表名映射为本地模型，并使用Django当前连接执行查询。它还拒绝包含外部数据库来源的表名。[入口读取](../backend/plugins/erp_base/source_phase6_entries.py#L144)、[本地表映射](../backend/plugins/erp_base/source_static_lookup.py#L142)、[本地连接](../backend/plugins/erp_base/source_static_lookup.py#L368)。
- `tools/legacy_snapshot`中的PowerShell脚本确实包含旧库连接字符串，用于开发提取。检查默认启动、应用代码时，没有发现它们被日常页面或保存流程自动启动。它们应退出客户部署范围。

这是代码和配置检查结论，没有关闭旧SQL Server或做实际交付包断开验证；不能据此提前宣布独立部署验收完成。

包括`SourceDyeOrderMain`、`SourceDyeFixedPrice`在内的655个原表模型，目前都是新系统的本地模型。它们保留旧字段形状，不能因名字带Source/旧表名就全部删除，否则会删除实际业务载体。

### 2.2 是否存在多余的新旧引用、对比和核验功能

**有。虽然不是持续在线访问旧库，前后端仍写入了过多面向开发参考、文件归档和迁移对照的实现，并且部分已经进入运行接口。**

|当前内容|实际读取/依赖|核实结果与调整方向|
|---|---|---|
|`LegacySourceViewSet.rows`|本地登记的旧导出文件及`.index`|读取原始文件，不读在线旧库。客户产品退出此API；开发需要时在外部工具查看|
|`LegacyMapViewSet.compare`|旧导出原行＋新库映射目标|逐字段对照，不是客户日常业务。退出客户路由、权限及菜单；按需保留离线开发脚本|
|`LegacyArchive.vue`|上述rows/compare接口|组件代码存在；本轮未发现其他前端文件导入挂载它，不能说当前一定可见。清理遗留组件，同时核查仍注册的后台资源|
|`OriginalEntryWorkbench.vue`|旧入口目录、支持状态和本地业务查询|`BusinessPane`维护模式仍挂载，显示旧库核验、复刻差异、开发核验/历史对账/现场验收。开发状态退出产品；有业务用途的查询保留为明确业务入口|
|`phase6_catalog`、公式逐字段核验、版式Proof|随程序携带的清单/模板、局部业务试算|覆盖检查和证明退出客户API，实际计算仍留在service。打印仍暂缓|
|`legacy_import_*`、`legacy_compare_business`等命令|导出清单、JSONL、新库|开发/一次性迁移工具，非客户正式操作步骤；不由启动、初始化、任务自动执行|
|历史Excel导入|上传xlsx、新库、导入权限、开发目录文件|不连接旧库，但与旧项目迁移身份绑定过多，必须解耦，见下一节|
|原旧平台收藏、功能改号和旧授权|新库中的旧平台配置记录|不是在线控制旧ERP，也不能管理新版Django权限；退出客户可执行API，必要历史值另行保留|
|655个原表模型和实际报价/工卡/库存服务|新库本地业务记录|保留实际业务。只有重复或无客户用途的模型/服务才逐项退役，不能按Source前缀删除|
|本地报价来源、转单来源、操作及撤销记录|新库本地单据和必要快照|是真实业务追溯，保留；不得改成每次读取旧文件或外部旧库|

关键依据：[原文件及对照API](../backend/plugins/erp_base/legacy_views.py)、[文件读取服务](../backend/plugins/erp_base/legacy_services.py)、[前端遗留对照组件](../web/src/plugins/erp/LegacyArchive.vue)、[旧入口工作台](../web/src/plugins/erp/OriginalEntryWorkbench.vue)、[实际挂载位置](../web/src/plugins/erp/BusinessPane.vue#L135)、[资源登记](../backend/plugins/erp_base/legacy_resources.py)、[系统菜单归属](../backend/system/management_layout.py#L37)。

### 2.3 Excel导入中已经查明的特定旧项目耦合

以下是整改前代码事实，保留作为问题依据；本轮处理结果见实施清单：

1. [source_excel_history.py](../backend/plugins/erp_base/source_excel_history.py#L41)把批次`database_name`固定写为`Textile_GXHFRS`。这是元数据标签，不是数据库连接，但客户导入不应被标成来自这个特定旧库。
2. [source_excel.py](../backend/plugins/erp_base/source_excel.py#L50)的历史导入需要`erp_base_legacyimportbatch`新增权限。客户导入对应资料应使用明确的资料导入权限，不应另外申请旧资料档案权限。
3. 同文件的`excel_finish`会调用`source_import.entries/link_relations`；[source_import.py](../backend/plugins/erp_base/source_import.py#L14)从`tools/legacy_models/source_catalog.json`读取目录。客户上传xlsx后，关系建立不应依赖开发工具目录。
4. `SourceRecord`的`source_batch/source_row`、[source_provenance.py](../backend/plugins/erp_base/source_provenance.py)和部分逆向上下文已经参与历史识别。不能把四个Legacy模型或两个来源字段直接删掉，否则会影响现有导入和历史业务行为。先把真实用途替换成新系统内的导入身份/业务关系，再处理废弃结构。

客户已经拿到的xlsx应纳入兼容核查：不能让用户为清理开发代码重新填几百份资料。后续实现时更新导入设置、权限和说明；原值承接、普通新增两类真实语义保留，去掉特定旧数据库及快照要求。

## 3. 纠正上一份方案的处理方式

|原安排/误区|本次明确修正|
|---|---|
|开发核验放进系统管理/维护入口就算收敛|不够。客户交付中的菜单、前端引用、API、权限登记、自动任务及默认初始化都要退出；需要时作为交付外的离线开发工具|
|客户需要完整历史对账后才能使用|不成立。客户可以自行导入并从新业务开始；本地导入核对和实际流程验证必做，旧全历史核对只在用户另行选择迁移范围时开展|
|旧配置“有表”就按普通业务资源复刻|不成立。参考旧业务与复制旧低代码平台分开；原窗体、网格、收藏、客户端版本、旧权限不是默认客户产品能力|
|旧库原键就是今后客户资料身份来源|不成立。新记录使用新系统自身记录ID及业务编号；旧原字段保留既有用途，手工输入/编号规则按客户新系统运行，不要求旧数据映射|
|新旧对照是所有客户长期要用的管理功能|不成立。先前提出的对比需求属于开发/迁移参考用途，不能据此默认建设长期对照产品|
|为了报表和扫码有数，再采用一套整理模型|不成立。同一真实业务确定本地权威模型；报表、扫码、权限和转单接同一链，不能要求重复导入/录入|
|把所有含legacy/source的文件删掉|不成立。名字不是删除依据；实际报价、计算、库存和逆向服务必须保留，只清理无关实现及外部参考依赖|
|后端只隐藏按钮或标维护即可|不成立。非业务接口必须退出默认注册，不能继续泛化挂到全部资源|

上一份核查的13项代码问题仍成立；处理建议以本方案为准，尤其是F05/F06/F12/F13。原统计只是现状盘点，不是客户最终应有的模型/功能数量。

## 4. 固定整改清单和执行顺序

以下12项是本轮固定整改范围。现已按[实施清单与验证](2026-10-24客户独立使用ERP整改实施清单与验证.md)落实客户独立运行整改，具体开发、本地导入及现场边界以实施记录为准。按顺序完成可执行开发与必要验证，不按用户未要求的“全历史复刻证明”扩张范围。

|编号|工作|完成标准|
|---|---|---|
|C01|固定客户业务范围与本地主链|逐业务列清模型、入口、service及本地引用；区分真实不同订单/业务和重复备用体系；不把全部旧配置当客户需求|
|C02|移出前端开发核验及旧平台入口|清理工作台/对照遗留组件、挂载、菜单、说明、开发阶段文案；保留实际报价选取、生产质量查询、必要业务维护|
|C03|收紧后端动作和资源注册|开发核验/原文件浏览/新旧对照/旧平台执行不默认注册；订单、采购等写动作只注册到适用资源；后台权限目录同步收敛|
|C04|开发提取与迁移工具退出客户部署|旧SQL连接脚本、快照抽取、复刻覆盖核查、逐字段对账留在交付外；默认启动、初始化、队列和部署不调用，不需要它们的目录|
|C05|客户Excel导入解耦|页面与xlsx对应业务资料；去掉固定旧库名、快照登记和旧档案权限前置；导入所需关系元数据独立于tools目录，不增加另一套执行框架|
|C06|本地导入和历史身份依赖收敛|逐项处理四个Legacy模型、source_batch/source_row及消费者；保留真实批次/行错误定位和逆向事实，已有记录可继续读改；无旧快照的新增和导入可用|
|C07|统一报表、扫码与实际业务链|修正12项整理模型报表和3类扫码的数据来源；新录订单、报工、员工卡、包装在对应入口可查；保留全部重复候选和业务状态|
|C08|审批与岗位权限按实际业务收敛|退出无依据的通用草稿/确认门槛；按单据真实审核、撤销、父子关系办理；岗位无需叠加“全库原资料”角色才能用主链|
|C09|退役重复备用业务体系|核查101个整理业务模型的实际用途、引用和已有记录；重复模型不再形成另一套可写客户链；实际不同业务继续保留，不直接清空或删表|
|C10|保留实际service，减去无关记录和平台行为|保留计算、转单、库存、质量和逆向；退出成功校验的重复整对象诊断记录、演示初始化及demo任务；有真实任务用途的基础能力保留|
|C11|全新独立库及浏览器验证|使用无旧快照的干净业务库完成资料导入、报价→订单→开卡/工艺/排产→生产/质量→包装/收发及逆向；旧SQL和开发导出目录不可用时仍可办理|
|C12|整理交付、说明及结果|客户说明只写本系统的配置、导入和业务操作；明确开发完成、本地导入核对、现场验收状态；财务/打印/35查询仍暂缓；新旧参考资料不混入客户必需数据|

执行中按实际业务改已有service，不为本次整改新建通用工作流、核验中心、迁移平台、同步平台或功能管理引擎。代码职责调整优先保持现有可验证业务行为；不为清理名字全量重命名数据库表、原字段和外键。

## 5. 客户使用流程

1. 配置新系统自己的数据库，初始化管理员、岗位及系统必须的配置。标准枚举/业务代码与客户业务资料明确区分，不把开发测试客户、物料、报价当默认正式资料。
2. 客户按业务顺序手工导入组织、人员、客户、供应商、物料、单位、仓库、机台/工序等需要的资料，也可在页面新增；无数据的少用资料不要求先导入才能打开系统。
3. 客户导入/录入本地染整报价、工艺和路线等实际使用资料；报价属于业务价格资料，按现有分类单独管理。
4. 新建订单时选本地客户、物料和本地报价；后续工卡、配方、排程、报工、质量、包装和收发均引用本地记录。
5. 查询/报表、审批/反审、转单/撤销、附件及导出围绕本次实际业务办理。需要原值历史导入时，用户明确选择，系统不重演历史库存和生产事件。

普通新增与原值导入不能混淆：保留原值的导入不意味着每行必须有旧库行号，普通新增也不能为了摆脱旧库而把历史单据自动改成新单执行。

## 6. 验证和“完成”标准

### 6.1 客户独立运行

- 新库无任何旧业务批次/映射时，账号登录、菜单、资料新增/导入、编号、单据保存和联动可用。
- 不提供旧SQL连接信息；独立验证环境不启用旧SQL服务，也不挂载开发导出、JSONL及索引目录，验证仍通过。为测试隔离不停止本机用户正在使用的其他服务。
- 客户部署保留真正业务计算需要的静态配置，但不依赖开发核验清单。对混合文件先拆出必要业务定义，再移出核验部分，不能简单删除导致保存公式失效。
- 不出现旧库查询、旧新对照或复刻核验的前端请求；无关接口不再由默认路由和权限目录注册。开发脚本不是客户运行依赖。
- 对真实设备采集继续使用新系统自己的接收协议和本地资料；缺少现场协议的事实单列，不能用旧库读数或伪回传代替。

### 6.2 客户手工导入

- 既有xlsx兼容或提供明确可直接使用的新版；必填、可空、自动编号、关联编码和导入顺序与当前代码一致。
- 仅导入一小套全新客户资料即可建立真实链，不依赖某批旧测试记录、开发电脑路径、旧库名、旧快照或旧映射。
- NULL、空串、0、负值、重复编码/同名、多候选和停用资料按实际字段及业务规则保留；真实约束冲突逐行给出原因，不悄悄去重、跳行或猜选关联。
- 原值导入不重复记库存/产量、不自动补造审核；普通新单保存执行明确的业务事件；同一业务对象不同时写两套主档/库存账。
- 导入错误定位、用户、文件、时间及本地记录可追查。这是客户导入职责，不需要附带旧数据库逐字段对账系统。

### 6.3 状态分开

|状态|本方案中的含义|
|---|---|
|方案已更新|本次完成，范围和待改项明确，不表示代码已经整改|
|开发完成|对应代码、路由/权限、导入、独立库及浏览器验证通过；无关开发功能退出默认客户交付|
|本地导入核对|针对用户上传文件核对新库记录、原值、关系及业务后果，不连接旧库即可完成|
|旧历史对照|仅在用户另行指定的数据迁移/开发核验范围开展；不是客户日常使用或从空库启用的前置条件|
|现场验收|实际岗位、设备、单位及生产流程由真实操作验证；开发通过不能冒充现场已验收|

## 7. 数据和既有实现的处理边界

目前不删除任何业务数据或模型字段。C06/C09实施前检查现有记录和依赖；需要退役的结构先解除应用依赖并保留既有资料可追溯，再做明确迁移，不能直接级联删除。不得恢复额外【旧erpID】。

“移出客户交付”不等于删除参考证据。旧表结构、业务说明、异常清单和开发验证可保存在项目开发资料中，但不注册成客户功能，不要求客户携带旧数据文件。真正有客户用途的历史业务数据仍须支持本地录入、导入及办理。
