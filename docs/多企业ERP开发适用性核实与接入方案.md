## 结论

当前框架可以作为后续 ERP 的开发基础。最贴合现有结构的交付方式是：维护共同的框架和业务代码，每家客户独立运行实例、数据库及附件目录，按客户启用相应业务应用。

它当前不是具备企业隔离的多租户 ERP，也不是已经完成采购、销售、库存、财务业务的 ERP 成品。具备管理平台能力、能够添加模型和页面，与已经满足客户业务要求，是不同的验收结论。

| 使用方式 | 当前判断 | 需要完成的工作 |
| --- | --- | --- |
| 每家企业独立服务器或电脑部署，分别开发客户业务 | 可以以此开始研发 | 准备客户配置、业务应用、数据备份及实际交付验收 |
| 一台服务器运行多家客户的独立实例 | 可采用此架构，但现有启动配置不能直接重复使用 | 分开数据目录、端口、密钥、Redis/任务服务和访问入口，并验证互不影响 |
| 一个网站、一个应用实例、一个数据库同时承载多家互不相关的企业 | 当前不满足 | 先设计企业身份及完整隔离链，不能用部门树直接代替 |
| 同一集团中多家公司共用一套业务 | 需要进一步开发 | 独立定义公司、账套、仓库、人员归属及跨公司业务规则，现有部门模型不包含这些业务语义 |

“每家独立部署”不要求每家复制一份失去同步的源码：可以保留共同代码，分别构建或配置客户版本。当前插件登记在代码中进行，尚无客户模块开关和统一实例管理平台；它们是否需要开发，取决于实际交付方式。

## 企业隔离核实

当前业务公共模型有 `creator`、`modifier`、`dept_belong`，没有统一的企业或租户字段。默认注册的 20 个 system 模型也未发现 `tenant`、`company` 或 `enterprise` 字段。运行时核实见 [erp-readiness-runtime-20261010.json](H:/Project_python/django-vue3-admin/djangovue3/docs/erp-readiness-runtime-20261010.json)。

`scoped_queryset()` 的实际规则是部门/创建人权限；超级管理员、全部数据授权及不启用数据范围的白名单会绕过部门过滤。模型没有 `dept_belong` 时也直接返回原查询集。它没有另外施加不可被普通角色授权解除的企业边界。

用户名和角色编码等在整个数据库唯一；企业各自使用同名用户名、同名角色编码的规则也没有建立。配置、消息接收、文件、任务结果等没有完整企业上下文。

因此，不能通过“创建两个顶级部门，再为管理员授予各自部门”便声称完成多租户。企业隔离需要覆盖查询、写入、关系选择、导入导出、附件实际访问、消息和后台任务；此次没有把缺失的隔离能力列为已通过。

不同独立客户实例还需要分开：

1. SQLite 数据库及附件目录。
2. 签名密钥、网站入口和服务端口。
3. Celery broker、worker、beat 和任务结果所属实例。
4. Redis 消息通道。

当前默认 broker 使用同一 Redis 地址的 `/3`，任务没有客户路由；导出任务按 `item_id` 从 worker 所连接的数据库读取记录。两个实例若共用队列，可能由另一实例的 worker 执行，不能只分开 SQLite 文件。

消息通道名目前是 `messages:{user_id}`。独立数据库中的用户 ID 可以相同，因而共享 Redis 时通道会重合；消息 payload 当前仅为变化通知，不能把它夸大成已观察到跨企业消息正文泄漏。Redis Pub/Sub 不按逻辑数据库编号隔离，因此仅换 Redis DB 编号不能完成消息隔离。[Redis 官方作用域说明](https://redis.io/docs/latest/develop/pubsub/#database--scoping)

初期可使用每家独立 Redis 实例，减少共享服务的改造量；若以后共用 Redis，再统一实现任务队列及消息通道命名空间。此处是架构建议，尚未修改代码。

## SQLite 与 ERP 业务边界

实测运行版本为 Python 3.14.8、Django 5.2.18；数据库保持 SQLite，事务模式为 `IMMEDIATE`，遵守用户既有版本和数据库要求。

SQLite 可以继续用于独立客户实例，但当前没有依据承诺任意客户规模、任意同时写入数量或大型批量业务都满足性能要求。项目历史并发脚本只是两个线程各 20 次调度/管理事务的验证，不是 ERP 容量测试。

- SQLite 的写事务存在竞争；现有 `IMMEDIATE` 调整获取写锁的时机，不会变成行级锁或实现无限并发写入。
- SQLite 不支持 `SELECT FOR UPDATE`；Django 的该方法在 SQLite 上不提供行锁。运行时 `has_select_for_update=false`。
- SQLite 没有真正的十进制定点内部类型。不能因为存在 `DecimalField` 示例，就认定数据库金额汇总、税额和成本计算已验证精确。

这些限制核对了 [Django 5.2 官方 SQLite 说明](https://docs.djangoproject.com/en/5.2/ref/databases/#sqlite-notes)。

维持 SQLite 的开发方向：金额/数量按实际业务定义精度和舍入；需要精确存储的金额可采用明确最小单位的整数，计算使用 Python Decimal，并验证汇总及往返导入。涉及库存扣减和单据过账时编写短事务、条件更新及业务状态规则。采用哪种金额单位、是否允许负库存等，须由具体模块确定，当前没有擅自设定。

先用一个客户的真实业务规模验证录单、出入库、后台任务及批量导入同时发生的情形，再给出容量结论。此建议没有改换数据库，也没有设置未经测量的用户人数上限。

## 尚需业务开发的内容

当前没有采购、销售、仓库、库存流水、生产、BOM、成本、应收应付、财务凭证等完整业务模块，也没有通用审批引擎。它们属于后续 ERP 研发范围，不是通过复刻管理平台即可自动获得的功能。

基础资料适合通用 CRUD。订单审核、出入库、反审核、过账和冲销，需要业务服务和相应事务：例如一次出库不能因重复提交而扣两次库存，作废单据不能继续过账。这些是具体业务正确性要求，不是为了保险任意增加的限制。

通用接口能直接新增、修改模型；如果已审核单据或库存流水仍暴露通用写入口，客户可能绕过专用业务流程。接入时应明确哪些模型使用通用 CRUD，哪些通过专用接口操作，可利用已有模型排除机制。不能只隐藏前端按钮便认为后台业务流程已受控。

客户定制可放在独立 Django 应用和前端插件中；客户字段应归入对应业务模型，避免在系统用户、角色及公共模型中堆放每家企业独有的字段。当前扩展能力是源码接入，不是无需写代码的客户流程设计器。

## 客户交付前需要补齐的工作

| 项目 | 当前观察 | 最小处理方向 |
| --- | --- | --- |
| 日常导航 | 正式网页证据出现“本机 iframe 验收”；分栏布局偏好被保存 | 制作客户基础数据时清理测试菜单，示例入口按交付需求启用，采用约定布局 |
| 客户配置 | APPS/URLS 静态登记；配置有开发默认值 | 明确每个客户的启用应用、独立密钥、入口和数据目录 |
| 网页服务部署 | 启动脚本、桌面包监听 127.0.0.1 | 单机可用；多人局域网访问需配置服务入口和绑定方式，不能直接把本机包当已完成部署 |
| 文件访问 | 开发 URL 配置通过 static() 提供 media；文件记录权限与 URL 访问分开 | 客户存在敏感附件时确定真实下载权限；关闭 DEBUG 后也需配置文件服务 |
| 异步任务 | Windows worker 为 solo；Redis 默认关闭持久化 | 验证长任务对队列的影响；交付前明确任务在进程/机器重启时是否允许丢失，再按业务要求配置持久化 |
| 备份恢复 | 有历史发布备份和数据导入工具，未见完整客户备份恢复流程 | 覆盖 SQLite、附件、配置及版本，执行一次真实恢复；初始化 JSON 不替代完整备份 |
| 升级 | 已有 Django 迁移及历史保留数据发布记录 | 对每个客户版本记录迁移、配置和升级结果，不覆盖客户数据 |
| 性能 | 当前验证以管理平台及小规模专项为主 | 用首个客户的真实数据量和操作组合验证，包含业务正确性及响应时间 |

这些是面向实际交付的工作，不意味着需要先开发插件市场、通用工作流、分布式系统或统一客户运维平台。

## 建议实施顺序

1. 采用每家客户独立实例作为起步交付方式，整理共同框架、客户配置、正式菜单和独立运行配置；如最终采用共享网站，先改做企业隔离设计。
2. 开发首个客户需要的基础资料，按模型接入现有权限、查询和 xlsx。
3. 按一个完整业务闭环开发单据、审核/执行动作及业务流水；不要把完整 ERP 一次性拆成大量空模块。
4. 将客户独有逻辑放在对应应用，复用共同模块和测试；验证升级、恢复及真实业务负载后交付。

本次没有向项目加入多租户、审批或其他新功能，也没有改变用户指定的 Python、Django 和 SQLite。以上交付方式是根据当前代码给出的建议，不代表用户已经选择或授权实施某一种多企业架构。
