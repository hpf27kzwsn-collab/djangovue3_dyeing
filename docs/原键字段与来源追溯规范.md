# 原键字段与来源追溯规范

生效日期：2026-10-16。本规范取代此前“所有模型额外添加旧erpID”的设计要求，适用于七个 ERP 模块的当前代码及后续开发。

## 模型及原字段

所有 ERP 模型取消额外的 `legacy_id` 字段，质量数量投影取消 `header_legacy_id`。不新增一个改名的通用旧 ID 字段作为替代。

Django 内部 `id` 用于新系统关联；旧表原有主键、联合主键各列、实际自增列、业务编号和明细号保持原类型、精度及值。客户按 CustomerID，联合键按全部原键列核对。原 SQL 自增列不因自增属性而被假定具有未声明的唯一约束。

## 原行承接及对比

原表复刻模型保留已有 `source_batch` 和 `source_row`，分别表示抽取批次与本次抽取行号。这两个字段不是新的业务编号，行号不能跨抽取批次识别同一业务记录。

完整承接保留每一原行，包括 NULL、负数、空字符串、孤立关联、相同条码和完全相同的重复记录。每个批次独立保留，不用业务码或内容摘要去重。相同批次再次执行整表导入应明确返回已经承接，使用对比入口核验；不追加一套相同批次行。

对保存的同次来源文件，按批次及提取行号定位并逐字段比较，原主键也是比较字段。比较核对完整行数和重复次数，不以合计或抽样替代。跨批次查找已转换的主档时，使用“源数据库、架构、表、全部原键列”的既有映射；多目标、值变化或重复原键不猜测覆盖。原形模型仍保存本批全部原行。

无可靠键的表不能推断跨批次哪一行发生了修改。对比可报告内容及各内容的出现次数差异，不得把相同内容合并成一条，也不得把提取行号误认成永久主键。当前逐表验证接口比较同一批次原文件；跨批次业务变更识别须明确对应规则后实现。

通用主档导入先逐行保存到原表复刻模型，再尝试采用到主档。无主键、重复原键、转换不兼容等情况仍返回已保存原行，并登记不能采用到通用主档的原因。来源映射使用现有 LegacyObjectMap；不在每张业务表重复存储序列化原键。

## 历史业务及派生记录

原表记录是否来自历史导入由来源批次识别，不根据旧主键是否有值判断。新业务也可以使用真实业务编号。导入不执行新单据触发、重算或库存动作；明确办理历史接续和逆向仍按相应 service 执行。

派生单据保留现有办理上下文中的来源快照和逐行关联。半年归档复制原字段，批次及提取行号留空；归档上下文明确指向原记录，用于识别其历史来源，不伪造一条备份表的原提取行，也不混入原批次的逐行对比。

报表的 `source` 是从当前原键字段、表和来源批次即时组织的展示信息，不是数据库额外 ID 列。原表无主键时 key 为 `{}`，仍保留批次和行号信息。

质量数量投影分别保留 `detail_no`（原明细号）、`detail_sheet_series`（原明细中的表头流水）、`header_sheet_series`（实际匹配表头的原流水）。后者来自真实连接结果，不能用前者补齐不存在的表头。每个连接行完整保留。

## 升级及后续开发

升级先备份待删除列并核验既有来源映射，再新增迁移删除字段。旧迁移保留其历史定义；新装数据库执行完整迁移后最终结构无这些额外列。数据库回退重新加列不会自动恢复已删除的值，需采用本次删列前备份恢复。

页面、字段权限、生成脚本、导出和测试均使用上述规则。历史实施记录及验证 JSON 中的旧字段名称只说明当时的验证事实，不是后续建设要求；不得修改历史验证数值来冒称重新执行过验证。

财务系统仍暂不开发。未使用、异常和重复业务不因本次标识调整而删除或跳过。
