## 2. 第一批：染整报价真正关联到染整订单

### 2.1 先固定实际对象与字段

|业务对象|旧物理表/当前模型|本批使用的原字段及含义|
|---|---|---|
|染整报价头|FixedPrice / erp_sales.SourceDyeFixedPrice|SheetSeries、SheetNo、SheetDate、CustomerID；原业务入口名为Quote|
|染整报价明细|FixedPriceDetail / erp_sales.SourceDyeFixedPriceDetail|DetailNo、SheetSeries、ProdID、YarnCategory、PriceUnit、CusPrice、Price、ProcessPrice、Pricesum、FenTouPrice、MinAmount；原入口名为QuoteDetail|
|染整订单头|OrderMain / erp_sales.SourceDyeOrderMain|SheetSeries、SheetNo、CustomerID、PriceUnit；不要与整理SalesOrder模型混接|
|染整订单颜色行|OrderColor / erp_sales.SourceDyeOrderColor|CheckNo、SheetSeries、ProdID、OrderQty、Unit、Price、Amount、ProcessPrice，以及原有数量字段|
|采用来源与操作记录|现有SourceDocumentContext.effects及BusinessAction|记录本次实际选择的报价原行、采用价格/单位/供纱方式、计算依据及前后变化；复用现有模型|

原入口Quote/QuoteDetail指向FixedPrice/FixedPriceDetail；旧物理Quote/QuoteDetail是另外的表。**不能把现有针对物理Quote/QuoteDetail的替代转单服务直接当成本批染整报价到订单的实现。** 原缺失视图仍按原35查询的安排暂缓。

OrderColor没有原YarnCategory/PriceUnit列，OrderMain也没有本批所需的原订单总金额列。供纱方式和本行计价单位存入采用上下文，订单头原PriceUnit仅在口径明确且适合全单时使用；订单总额从明细计算展示，不为了联动随意加一套原字段。

### 2.2 用户在订单里的实际操作

1. 新建染整订单并选择客户；新增颜色明细，选择物料，录入数量和数量单位。
2. 在本颜色行选择供纱方式，系统按“客户＋物料＋供纱方式”列出对应染整报价。
3. 界面显示报价单号、日期、物料、供纱方式、对客报价、客确价、总单价、原计价单位。匹配记录唯一且计价口径明确时可带出候选；多条时逐条列出，由用户明确采用，不按日期任取一条。
4. 采用默认以CusPrice“对客报价”为订单染整单价来源，显示本次计价单位和数量。需要采用客确价或手工议价时必须明确选择价格依据，不悄悄切换列。
5. service按所选价格和数量计算本行金额，同时保存采用来源。页面保存、整单保存和专用采用动作必须得到相同结果。
6. 再次打开订单，能看到本行采用的报价单及当时单价；新增报价、修改报价、修改订单时按下文规则处理。

这里的“采用报价”是本项目将旧报价资料用于日常订单的明确业务动作；不能声称历史每一张旧订单原来都保存了该引用。

### 2.3 匹配与价格采用规则

|事项|明确规则|
|---|---|
|客户|使用本订单头CustomerID，不跨客户套价|
|物料|按ProdID原编码匹配，不按名称模糊相似匹配，不将成分/纤维类别当物料编码|
|供纱方式|使用原Z010：本厂采购＝包工包料；客户来纱＝来料加工。订单里明确选择，不从名称或缺值猜测|
|常用价格|默认采用FixedPriceDetail.CusPrice；Price是客确价格，Pricesum是总单价，三者不混用|
|重复/多条报价|全部候选保留；同价多条也保留各自身份，不合并为一条；用户明确选定实际来源|
|日期|显示原报价日期。旧现存日期不足以证明全部历史生效区间，不自动将“最新”解释成订单日期当时有效价|
|NULL与0|缺价不能当作0；真实0价和负价原值可以保留并明确显示；不以Price>0过滤掉本批实际使用的CusPrice报价|
|没有匹配报价|允许保存尚未计价的原单据，或明确手工录价；显示缺价，不自动套别的客户/物料，不伪造报价来源|
|分头费/最低消费/另收费|保留原FenTouPrice、MinAmount、ProcessPrice；本批先完成明确的染整基础金额，不擅自叠加或与CusPrice重复计算。原收费服务继续保留，扩展计算须单独列规则和验收|

现有[source_phase2_functions.confirmed_price](../backend/plugins/erp_base/source_phase2_functions.py)含TOP 1按日期取价、无价返回0及另收费逻辑，保留它的原语义供旧功能使用。新增订单候选/采用服务复用原模型、匹配工具和字段转换，不直接把该旧单值返回结果当作订单选价依据。

### 2.4 单位、数量和金额

|原C010值|原含义|本批金额处理|
|---|---|---|
|1|元/kg|OrderColor.Unit为KG/kg时使用OrderQty；本行金额＝数量×采用单价|
|2|元/吨|数量本身为吨时直接采用；来源明确为KG时按1000KG＝1吨换算，记录换算前后数量|
|3|元/米|须有明确的米数量来源；不能把KG重量当长度|
|4|元/条|须有明确计价条数；原OrderRolls标题为“订单粒数”，不能未经依据就当条数|
|5|元/缸|采用明确的订单缸数依据；不混用前处理缸数、实际开缸次数或重量|
|6|元/码|须有明确码数来源；不能把OutYard等后续收发字段直接当下单数量|

六种原单位都保留候选和手工录入，不因少用删除。首批优先验收KG订单；其余按明确数量来源完成，暂未取得来源时保留原价/原单位并允许人工指定本单计价数量或保留未计价，不能默算KG金额或跳过该行。

现存847条报价明细PriceUnit全部NULL。采用这批旧报价时，在订单采用界面明确本单单位；对KG订单可预选“元/kg”并显示这是本次采用口径，随保存记录到上下文，**不回写旧报价为空的PriceUnit，不将分析假设伪装成旧单位已核实。**

数量采用当前OrderQty；现有GrayQty→OrderQty原默认规则继续保留，明确手填的OrderQty优先。不能为了计算金额换成实称、包装量或实际收发量。

单价写入OrderColor.Price（现有Decimal(8,2)），金额写入Amount（Decimal(10,2)）；采用Decimal计算并按现有字段精度存储，不由前端浮点数决定正式金额。不新增OrderMain总金额字段：全部行已计价时显示合计；存在未计价行时显示“已计价小计＋未计价行数”，不能将部分合计冒充整单金额。

### 2.5 来源保存与修改行为

|触发|本批行为|
|---|---|
|首次采用报价|同一事务保存订单行Price/Amount和所选报价来源；来源记录含报价头/明细当前记录ID、原SheetSeries/DetailNo及原来源批次/提取行（如有）、原CusPrice、采用价格列/单价/单位、供纱方式、数量和计算结果|
|保存来源|复用SourceDocumentContext.effects中的订单选价记录及BusinessAction审计；价格按十进制文本保存快照。内部记录ID仅是实际外键/上下文定位，不是新增【旧erpID】字段|
|只改重量|有有效采用来源时按已采用单价重算金额；未改变的报价来源保留；本次明确手工金额按人工方式记录，不被自动公式覆盖|
|改客户、物料、供纱方式或计价口径|原自动采用关系失效，保留旧采用审计；界面要求重新选价或明确手工价格。不得继续把旧来源当作新物料报价；本次未手填新价格时，旧自动派生Price/Amount退出当前有效值，旧值仍在审计中保留|
|修改报价资料|不自动改已保存订单单价/金额；旧采用值有快照，页面可对照当前报价|
|删除或退出生效的报价|遵守既有报价删除规则；已采用订单保留当时快照，不级联清空订单，不把已删除来源显示成仍存在|
|重新取价|用户明确触发、选定候选，再按同一service更新本次采用和金额，记录前后差异|
|手工议价/明确改价|保留输入并登记人工依据；不强造一个报价来源，不被后续自动刷新覆盖|
|历史订单|Price/Amount为NULL或其他原值仍原样保留；不因当前存在报价而批量补写历史成交单价/金额，也不伪造历史采用记录|
|普通Excel业务录入|与普通页面走同一保存服务；明确提供的价格/金额优先，不能仅因匹配到报价就静默改写；如需采用报价须通过明确采用信息或保存后选价|
|历史资料承接|继续使用历史承接方式，原值照存，不触发新选价、编号、状态或库存事件；本批不改现有历史xlsx原值|
|只改备注等无关字段|不重新选价、不重新采用、不改变现有价格或金额|

不为所有旧订单强行设置“必须先有报价才能保存”。新选价服务负责这次明确发生的采用；历史缺价、重复报价和手工价格都必须能区分、保存和复查。
