# 业务服务与全量承接实施记录

日期：2026-10-14。分支：`feature/erp-seven-module-models`。七模块全部基础及业务仍为复刻目标，独立财务核算暂不实施。

## 已落地代码

1. 原表确认、审核、重新办理移到`source_services.py`；整单事务与主从写入移到`document_services.py`。接口处理参数、权限及响应，不在接口中编排业务生效。
2. 147种明确的原明细归属接入表头控制。关联明细及嵌套配方/称料明细随根表头冻结；整单失败回滚表头和前面已保存的明细。独立后续单据可引用已审核来源，原关联码按实际所选记录同步。
3. 保存最新已取得入口的326项证据、307条原公式、221条非空钩子SQL；台账状态仍区分已登记与已对照，未把证据数量当作实现数量。
4. 494项原SQL默认定义用于新录入未提供的字段；历史值、明确NULL、空串和0不被默认值覆盖。33个原自增字段采用独立编号服务；新增内部`SourceIdentitySequence`，当前660个ERP模型均含【旧erpID】。
5. 补齐`CustomerTSDetail`和`GrayMaterialDetail`两组明确主从FK，原列名`Sheetseries`与表头`SheetSeries`分别保留；再补`StuffWeightDetail`到`StuffWeightPhase`的复合键关系，累计161组。所有关系的原字段及目标字段由生成过程逐项检查。
6. 已证实的部分原金额、组成价、盘点差额、包装净重公式接入计算服务及页面。三种包装入口净重方法分别采用；染化料入库金额正算和单价反算分别处理。
7. 坯料入库、坯料出库、成品出库、染化料入库四类原表头合计在明细写入/删除/计算时同事务回写，按原SUM及明确ISNULL规则保留NULL、负数和零。
8. 交付单新增六位小数实际采用单价快照；保留原两位小数价格字段，避免来源报价已明确而原价NULL时不能交付或损失精度。
9. 新增逐原行身份及全部原字段核对服务和`legacy_compare_business`命令，不以样本、合计或文件哈希代替数据库原值对照。
10. 新增19种原表的66个具体入口计算选项：配方剂量金额、称料调整剂量/需用量/金额及浴比、来样色号、染化料单位、曲线参数、工卡计划汇总、成品入库及损耗、坯料与半成品明细汇总、包装完整入口、确价组成成本等。阶段和物料明细分别采用各自物理字段，原金额及损耗按原精度保存。选项数不代表旧页面或307条公式全部复刻，查询别名、表头确认价来源、生成时点等差异见异常E12～E14。

普通源表写入记录动作前后事实；历史导入直接保存原值，不重新办理旧单据、重算旧合计或生成重复库存。技术上的真实字段校验、主从事务和来源关系按对应业务实现，没有猜字段、多名称兼容、广泛吞异常、失败补零或默认父对象逻辑。

## 项目数据库及服务

项目SQLite已应用五个新增迁移：内部自增序列、交付精确单价、两组原主从FK和称料明细到阶段关系。迁移前备份：`data-backups/before-workflow-services-20261014.sqlite3`。入口及字段已初始化，原权限定制保留。

实际项目660个模型的表和【旧erpID】已核对，1,343条已有主档数量一致：734字典、33班次、274员工、182主体、120机台。原表历史正式录入数仍为零；独立试承接与正式采用分别记录。

开发服务地址为`http://127.0.0.1:8001`，启动方式`scripts/start.ps1 -Port 8001`。本轮8000端口被其他Node进程使用，未把该进程当成本项目后端停止。启动脚本显式支持端口参数，不自动尝试备用端口。

706次实际HTTP检查通过，覆盖660个模型元数据、12类报表及CSV、原表和内部序列查询、前端静态资源。模型与迁移一致性检查未发现未生成变更。

## 回归验证

第一轮24项PostgreSQL业务回归通过；主从、原公式、原行核对、销售、打样和包装交付43项复测通过。整个平台及业务完整回归260项通过，包含原有生产/库存并发用例；随后最终服务变化在独立5440实例复测15项，全部通过，覆盖表头回写、API原默认值、已审核来源的独立包装、关联码一致性及逐原行对照。15项服务复测采用直接建表，不能代替正式迁移；正式项目四个迁移及独立历史库完整正式迁移另有记录。

追加原入口公式及称料关联后，在独立5440实例新测试库最终复测35项全部通过，包括原来15项、12项新入口场景及8项源模型/迁移状态检查。覆盖原NeedQty金额与实际量的区别、工艺/洗缸不同除数、加料原零需用量、配方比例和浴比、NULL厚度、包装不同数量、带符号退货汇总，以及无需表头的本行公式不附加关联限制。工卡计划汇总保留已建立编号，采用原数字单位码，不把汇总动作混成生成编号。正式项目第五个迁移另行应用，模型一致性检查无待生成迁移，项目系统检查零问题；重启服务后接口HTTP 200。

## 全量历史试承接

独立PostgreSQL试承接库：`erp_history_trial_20261014`，位于本项目专用5439实例。来源为已经完整登记的91张原行表、9,055,094行。试承接用户是不可登录的内部导入操作者，不是旧业务主体或默认父项。

按完整来源逐表事务承接，原身份和全部字段流式核对同步推进。最终91表、9,055,094行全部承接，原身份、NULL/空串/0、符号、精度、二进制及所有原字段逐行核对通过，共415,914,238次字段比较。原配置/数据库明确关系唯一匹配填充5,470,738项；多匹配或无匹配保留原码、原行及可空关系，没有制造默认父项。

运行结果保存在项目忽略的运行目录：`full-history-import-progress.json`、`full-history-compare-progress.json`及对应日志，两份最终报告的`completed`均为true。承接过程中原专用实例的锁容量不足，未完成表的事务回滚；调整该实例容量后，以已完成日志和数据库行数核对接续，未跳过失败表或失败行。最终15项复测的5440实例已关闭；保留5439实例用于独立历史试承接库查看，不改正式项目数据库配置。

之后补称料明细到阶段关系时，同一个5439试承接库应用新迁移并填充1,204,175项关联，累计6,674,913项。完整重核`StuffWeightDetail`的1,204,177行、38,533,664个原字段值，全部一致；未能明确唯一关联的两行仍保留原码和全部原值。新增结果另存`history-weight-relations.json`，未覆盖前面91表的完成报告。35项复测临时重启5440，完成后关闭。

这是91表的全量试承接，不等于全部553张业务原表已经采集，也不等于项目正式采用全部历史。其他业务原行和当日最新字段还需要在旧连接可用时只读核实及补采。本轮尝试恢复默认SQL Server实例连接时，Windows服务权限拒绝启动；因此尚不能查询当前最新字段及未取得的原行，已保存证据继续用于开发。
