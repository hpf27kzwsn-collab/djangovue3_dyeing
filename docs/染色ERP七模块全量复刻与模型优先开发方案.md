## 1. 已确定目标与新的开发方式

完整还原旧ERP的全部基础资料和业务资料，包括模型、字段、关联、数量、状态、计算、录入及逆向流程。增加独立的【质量管理】，最终划分为七模块：基础信息、销售管理、采购管理、打样管理、生产管理、仓储管理、质量管理。

财务系统仍按此前要求暂不实施。排除的是独立财务核算及账款业务；基础、报价、订单、采购等共用资料和原有商务字段须逐项保留，不能因为某字段与财务有关就删掉对应业务记录。

采用新的工作顺序：**我先查证全部旧来源、补齐Django业务单据模型及字段，再做历史数据承接验证；确实无法复刻的事项最后单独集中提问。** 不以填写143道问答作为开始开发的前提，不反复询问是否要复刻低频业务。

以下要求已经确定，无须再次提问：

- 玉林恒纺一套系统统一管理；组织名称和实际归属采用用户G01的回答。
- 坯纱、坯布、染色、松筒、加捻、翻松、花灰、定型、外协等旧业务全部纳入。停用或低频不缩减模型和流程。
- 全部历史基础及业务数据都要由新模型及业务查询承接，不仅迁未结，不用原文件归档代替业务复刻。
- 负数、NULL、小数粒数、重复条码、缺关联、时间逆序等原记录，只要能够录入新系统就全部承接，不自动删、改、合并或跳过。
- 所有业务单据按用户G03要求具有草稿、确认、审核环节；旧历史状态及原有审批事实另有明确对应，不能虚构历史审核事件。
- 所有ERP模型取消额外旧 ID 字段；旧表真实主键和原字段保留，来源通过已有批次、提取行及映射表达。后续新增模型执行同一规则。
- 真正无法同形复刻时，列出具体来源、障碍、可行方案及影响交用户裁定。普通技术查询和可自行落实的结构调整由我完成。
- 不做防御性编程：按明确字段、来源和业务规则实现，不增加猜字段、隐藏默认、万能兼容、异常吞掉或计划填实称等逻辑。

实施可以有依赖顺序，但目标是全部完成，不划分开发者可以自行裁剪的“首期范围”。

## 2. 当前进度与需要纠正的基线

当前项目登记六个ERP应用，已有106个模型、45个ERP迁移；原键和来源关系按当前规范保留。质量检验和处置当前属于生产应用，质量应用尚未建立。

已经归档的是选定91张表、9,055,094行数据；实际进入新模型的为1,343条基础主档。资料包的旧表目录列有690个表条目，其中dbo35个、dye655个。**690条目录不是690个必建业务模型，91张已提取表也不是完整业务范围。** 财务、平台、字典、业务、历史副本及未知用途条目要逐项查证归属，不能按表名或行数自动过滤。

现有106个模型是可复用的基础，不能为维持这个数量把遗漏业务塞成备注，也不能只围绕91表继续开发。最终模型数量由完整旧业务覆盖清单决定。

已见需要继续核对的来源包括：外协申请主从、退料申请、坯布领取通知、半成品规格转换、配方关联、工序/人员记录、设备与能耗业务等。部分目录中文含义属于推断，按真实页面、字段和程序核实后确定归属。

本方案引用当前代码及现有归档作为依据；实施时再只读核对最新旧库字段和有效界面配置，不在旧库写入或修改结构。

## 4. 质量管理独立建模方案

### 4.1 现有模型迁入

| 当前模型 | 计划归属 | 处理 |
|---|---|---|
| `erp_production.QualityInspection` | `erp_quality.QualityInspection` | 保留原ID、原键字段及来源信息、字段及来料/工卡/执行等关联 |
| `erp_production.InspectionResultLine` | `erp_quality.InspectionResultLine` | 保留检验主从关系、原项目/槽位、实际值和原判定 |
| `erp_production.QualityDisposition` | `erp_quality.QualityDisposition` | 保留放行、让步、降级、返修等事实及包装覆盖关联 |
| `erp_production.QualityDefect` | `erp_quality.QualityDefect` | 保留原疵点、缺陷、状态、位置和处理资料 |

生产的`ReworkOrder`继续承接返修加工任务、路线和执行，引用质量处置和复检结果；质量模块负责判定、返修要求及复检。客户投诉原登记仍属销售，质量调查/处置通过关联承接；不在两个模块复制同一份库存或完工事实。

### 4.2 需要补齐的质量结构

- 原检验项目、标准、等级、判定码、项目单位及上下限等，按旧配置建明确字典/项目/标准明细。不能因目前没有独立标准模型就丢旧字段。
- 来料、过程、成品和复检的原主从、审核/确认、检验对象与覆盖范围。没有独立原检验主表时，根据真实旧QC入口和承载表建立对应，不凭模型名字虚造检验事件。
- `RecordYield`同时承载包装和Q1～Q15、T1～T5、结果等质量字段。分别确定字段去向，包装身份与质量结果关联，原槽位及原值保留。槽位名称暂不清楚时可先按原槽位标识存储，不等待用户逐槽解释才能建模。
- 原质量结果为空的包装记录仍完整保存；不能自动补“合格”，也不能为满足新检验必填要求拒绝该包装。
- `WDefect`按原现场疵点/异常资料对应，不把每条疵点强制改造成完整检验单。`SampleIn/Out`等名称候选按真实用途归入打样、质量或仓储，不能仅凭名字判定。

### 4.3 Django迁移和注册

新增`plugins/erp_quality`应用及独立菜单、资源、查询和权限。质量模型的归属变更采用独立迁移，优先通过明确的迁移状态调整保留现有物理表名、主键和数据；实际迁移实现以检查到的外键依赖为准。

同步调整生产、采购、仓储、销售等引用，质量服务、元数据、报表、字段权限及旧新映射的目标模型标识。已有审计原文和源身份不改写成另一个历史事实。不得删除旧表后重建来冒充无损迁移，不能重置现有岗位授权。

质量模块完整性验收包括模型归属、物理数据、主从/FK、菜单、字段权限、查询和跨模块引用；这不只是把菜单改名。

## 5. 先建立完整覆盖清单，再补模型

### 5.1 原系统覆盖清单

以全表目录、最新字段、有效页面、查询/保存程序、关系和原数据为证据，逐项登记：

| 必须登记的内容 | 说明 |
|---|---|
| 旧来源 | 原架构、表/视图/页面、程序及主键；一个业务可有多个来源 |
| 原字段 | 中文标题、实际类型、长度、精度、小数位、NULL、默认、表达式及字典 |
| 新归属 | 七模块中的模型及具体字段，主从/关联及业务入口 |
| 字段对应方式 | 原形复刻、明确归一化、明确派生/公共审计、多对象拆分及完整身份对应 |
| 数据范围 | 原总行数、旧身份集合、已承接数、未承接数及具体原因；原空表也登记模型结构 |
| 流程与计算 | 保存、确认、审核、反审核、完成、结案、取消、冲销、更正及实际公式 |
| 进度 | 已有待复核、需修订、需新增、待技术查证、真正无法复刻待用户裁定 |

不使用“不常用”“看起来异常”“缺单位”“外键找不到”作为排除状态。目录中的推断中文名和旧迁移建议仅是证据线索，不能继续采用“空表不建、低置信只留档”的旧建议。

### 5.2 现有模型复核

逐项检查现有字段和约束能否承接真实旧数据，特别是：

- 统一物料/主体/收发模型合并了哪些旧实体，原入口特有字段是否都存在。
- 包装条码全局唯一、数量正值、完工时间不得早于开工等现有约束是否是旧规则。没有依据且阻止真实数据进入的约束应修订，而不是将记录移到文件后跳过。
- 单位、状态、父单、工序、配方、检验和放行是否被增加了旧系统没有的强制前置；原可空值及缺关联怎样准确表达。
- 生产实绩、计划、实量、库存账面量及派生显示是否被错误合并；原字段值与新计算结果应能分别对照。
- 最新界面解释是否与英文名不同。例如机台`MinVatQty`必须核实最新标题与使用程序，不能凭“Min”或新字段名确定实际含义。

查证之后能确定的直接修订；字段含义尚不清但类型/来源明确的，先保存原字段和合理模块对应，登记“待解释”，不等于无法建模或不能导入。

### 5.3 补齐主从和关联模型

优先按真实原主从结构建模。旧表相似不必强行合并；只有关系和差异都能完整表达时才归一化。以下是已见候选，不是最终完整列表：

| 来源家族/候选 | 拟落点 | 需要完成 |
|---|---|---|
| `OutWorkApply/Detail`、`SemiOutWorkApply/Detail` | 生产外协申请/任务，关联仓储发出收回 | 补齐原主从和关系，全部历史承接；不能只用普通出库替代完整外协单据 |
| `GrayReturnApply/Detail` | 生产退料申请，关联仓储实际退回 | 保存原申请、数量、原因、审核及实物单据，不只有退料结果 |
| `GetClothNotice/Detail` | 根据原入口落实生产领料通知及仓储对应 | 保留通知和实际领料区别，物料类别以原字段为准 |
| `SemiStockSpecUp/Detail` | 仓储规格转换及明细 | 原规格、新规格、批次、数量和库存采用事实 |
| `DyeRecipeJob`及其他配方关联 | 打样配方资料/生产采用关系 | 原明确关联、原版本及引用；不按日期猜配方 |
| `WWorkRecord`、`JobShiftEmp`等 | 生产人员/班次与实际作业资料 | 原工作记录与刷卡时间分别保存，不扩展工资核算 |
| `EnergyConsumption/Detail`及设备资料 | 生产设备与非财务能耗记录，基础计量点 | 原读数、用量、单位、设备、周期和来源；成本分摊仍排除 |
| 原料/半成品/成品/染化料/物品的收发、盘点、调拨、调整家族 | 仓储主从/流水/余额 | 每家族完整字段和身份，旧空表仍具备模型/入口 |
| 旧QC页面、`RecordYield`质量字段、`WDefect`及相关字典 | 质量管理及包装关联 | 原项目、结果、数量、单位、判定和处置完整对应 |

业务归属不能证明的先继续查代码/配置；数据字段可先准确承接，不把技术查证全部变成用户问卷。

## 6. 旧数据承接的具体规则

### 6.1 保留原键字段，使用已有来源关系

所有 ERP 模型取消额外 `legacy_id`，不以改名的新列替代。原表中的 CustomerID、单据流水、明细号、联合主键各列及实际自增列均保留原值。Django 内部 id 用于新系统关联。

原表复刻记录用已有来源批次和提取行号定位本次抽取的每一行；已转换主档用 LegacyObjectMap 对应原表和完整原键。无可靠主键的表也完整保存，重复内容保留出现次数，提取行号不能作为跨批次业务主键。

验收检查所有当前模型和数据库不再存在额外旧 ID 列，原字段及已建立来源映射完整；历史记录识别、导入、比较和逆向业务不依赖已删除列。详见[原键字段与来源追溯规范](原键字段与来源追溯规范.md)。

### 6.2 不是先“清洗成正常”才能导入

| 原记录情况 | 模型及导入采用方式 |
|---|---|
| NULL、空串、0 | 分别保存；旧可空字段保持可空，不拿0、启用、草稿或当前时间填缺失 |
| 负数量、小数粒数 | 用能容纳原精度与符号的真实字段承接，不取绝对值/截整；原类型和逆向关系分别保存 |
| 相同条码多个包装 | 保留独立原记录及其工卡/箱号/原键；条码语义核对后按真实范围识别，不以全局唯一拒绝原行 |
| 结束早于开始、数秒刷卡 | 原时间原样保存；计算字段保留原计算依据，不能自动交换时间或造连续工时 |
| 子表缺父表、旧代码无对应 | 保存原子行及原父键/代码，新FK明确允许未对应；保留可查的未解析关系，不造默认父对象 |
| 计划量有值、实量为空、已自动出库 | 分别保存原计划、空实量和原出库量/来源；不能要求历史有实称才允许承接出库，也不能将计划复制成实称 |
| 旧状态无法直接对应新枚举 | 保存原状态值及原流程事实，明确新业务状态映射；尚未解释时也不把原行变草稿或丢弃 |
| 日期/数值精度超出当前Python/模型表达 | 明确补可保留原精确表示的字段并标出转换方式，例如时间有效第7位；不静默舍入后宣称无损 |
| 图片、附件、横向参数槽位 | 保存原文件及原槽位身份，逐项对应结构化字段/明细；不是只在通用备注里留一段说明 |

技术上可录入、可保留的内容直接落模型。“含义待确认”和“技术上无法表达”是两种状态：前者继续保存和查证，只有后者才进入真正无法复刻事项。

### 6.3 关系与新旧办理状态

历史加载直接保存原事实及对应，不通过新“确认/过账/完工”动作重演一次旧业务，避免制造重复库存或审批。已有真实审核日期、审核人和状态按源字段承接；旧没有发生的阶段不补虚构事件。

新业务的草稿、确认、审核分别建明确事实及岗位动作。自动生成的明细/流水遵循父单实际审核或生成来源，不要求每一条流水被人工独立审核；具体对照在模型清单中写清。

历史查询、原状态查询和对照要可用，不把有未解析关系的已承接记录隐藏掉。后续用户决定更正时保存原值和明确更正，不覆盖证据。

### 6.4 原库存全迁与实际余额计量

原库存流水、余额、收发及调整记录全部承接。正式库存采用按真实范围明确：若采用切换期初，旧流水仍在业务模型可查询但不再叠加一次；若历史重建则不重复加入同范围期初。该处理解决数量重复，不取消任何历史数据的复刻。

## 7. 实施顺序与每步完成标准

| 步骤 | 执行内容 | 完成标准 |
|---|---|---|
| 1 全来源覆盖 | 审核旧目录、页面、最新字段、程序及数据家族 | 所有基础/业务来源有去向；没有因为低频、空表或异常而排除的项 |
| 2 七模块定型 | 新建质量应用，确定基础和业务实体边界、原主从及字段 | 模型/字段/来源清单完整；质量归属和跨模块FK明确 |
| 3 全部模型落地 | 修订现有106模型并补新增模型、独立迁移、原码及状态字段 | 全部已识别旧业务可表达，旧数据类型及范围能存入；现有数据/权限保留 |
| 4 承接验证 | 在独立测试库加载真实主从样例，含NULL、负数、重复及孤儿等 | 原行、原键、字段与精度对照；可录入的原行没有跳过，失败原因逐项可定位 |
| 5 集中差异提问 | 模型基本齐全后只问仍真正无法复刻的事项 | 每题有旧证据、具体障碍、建议答案和影响，不发全业务泛问卷 |
| 6 完整功能与历史导入 | 按原流程补全部页面/动作/计算、草稿确认审核和逆向；逐模块扩展真实加载 | 七模块全部功能和历史对应完成，原总数/身份集合/数量逐项对账 |
| 7 实际采用 | 依据用户确定时点核对最新数据、未结接续、库存与设备实际联调 | 全数据不漏项，库存不重复；实际上线与数据复刻分别有明确验收结果 |

“先模型后提问”不是先做一个只有名字的空模型：字段、原键、主从、原码、状态及关键数量要一起建好，再用真实样例证明可承接。完整全量正式导入和实际切换仍在后续步骤，本方案不提前宣称已经完成。

## 8. 真正无法复刻事项的单独汇总方式

实施后单独交付《旧ERP无法同形复刻与需确认事项》，不继续让用户逐题填写原143道问卷。

每条固定登记：

| 项目 | 必须说明 |
|---|---|
| 编号与模块 | 指向七模块具体业务/模型/字段 |
| 旧来源与实例 | 原页面、表键、字段、程序及真实样例 |
| 已完成的查证 | 查过哪些资料和关系，哪些事实已确定 |
| 具体障碍 | 为什么技术上不能直接表达/办理；不能仅写“异常”或“低频” |
| 已能承接内容 | 原数据是否已存入对应模型，尚未对应什么；不隐藏差额 |
| 建议方案 | 首选合理对应、字段/流程变化及影响，用户可直接确认或修改 |
| 未采用影响 | 涉及原记录数、关联、计算和可办理功能 |
| 用户决定 | 待确认/确认方案及意见；没有答案不表示可以删除 |

普通缺名称、源字段可查、关系可保存、旧值可表达的问题由我先处理；只有查证后仍影响准确复刻的具体差异集中提交。现场设备型号/协议不足时，先完成相关任务和历史模型，真实设备接入参数另列，不阻塞无关业务建模。

## 9. 交付与验收

模型阶段交付：七模块模型、独立迁移、完整原表—字段—模型对照、主从/关联清单、现有约束修订清单、真实样例承接结果及真正无法复刻事项。所有表和字段的新增、修订、迁属、归一化及保留原表示都分别说明。

最终验收以原来源身份集合和字段完整性为核心：行数一致只是其中一项，还需原键、NULL/空串/0、精度、重复行、关联、状态、流程、计算和逆向事实逐项对照。一旧行拆多对象或多旧表归一化时，使用明确映射核对，不能简单比较新旧模型总行数。

失败的记录有完整来源和具体原因；可录入的必须进入新模型，不存在“跳过后继续并报告全量成功”。未覆盖字段、未承接行、未完成流程和未决差异分别列明，全部关闭后才能称完整复刻完成。

验收只做必要检查：空库执行正式迁移、已有数据无损迁移、质量迁属关系/权限、真实数据边界、原流程与计算、全量导入对照。前端构建或局部测试通过不能代替全部旧业务的覆盖证明。
