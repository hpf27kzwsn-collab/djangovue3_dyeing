## 2. 字段复刻的执行规则

| 项目 | 执行规则 |
| --- | --- |
| 已明确的事实含义 | 按当前旧入口复刻，不按英文列名猜中文业务含义；品牌、用途、特殊事项等独立保留 |
| 直接对应的文本 | 按旧 varchar/nvarchar/char/nchar 声明长度保存；max、text/ntext 使用 TextField；nvarchar 字节长度换算为字符长度 |
| 原文本空值 | 可直接对应的可空文本分别保留 NULL 和空串；没有旧列的新文本按明确的新业务定义处理 |
| 原布尔标志 | 保留 NULL、否、是三种情况；没有旧默认的可空标志不在模型中默认补成 True/False |
| 原值 Decimal | 可以直接原值保存的剂量、色度、幅宽、价格等按旧 precision/scale 定义，不把 decimal 的存储字节数当成精度 |
| 发生时间 | 保留旧 datetime 的完整日期时间，按上海时间解释；新系统审计时间与旧业务时间分开 |
| 业务代码及主键 | 保留文本、前导零及真实复合键，建立新 ID 映射；不通过名称或同号猜关联 |
| 页面设置 | 按对应旧页面记录的标题、编辑器、必填、只读、显示精度及表达式还原；配置未填写不等于 False 或 0 |
| 旧默认表达式 | 数据库默认、界面新建默认、已有历史空值分别处理；新建默认不能反向填入旧缺失事实 |
| 旧计算字段 | 复刻有依据的公式和计算口径；明确属于汇总的量由来源计算，不再作为第二套可写事实 |

代码仍使用明确的 Django 英文字段名和新内部外键。关联、版本及快照无法与旧物理列一一同形时，采用下一节的合理方案并登记差异。页面标题和说明能够保留旧术语，不要求把旧字符串键强行存进新外键。

## 4. 无法直接同形复刻的合理方案

| 差异 | 当前合理方案 | 后续实现要求 |
| --- | --- | --- |
| 多旧表合为同一主档 | 主体、物料、商业价格等使用统一模型；通过旧表名和完整键区分来源 | 保留各入口对应标题和来源，不能因为同号合并不同旧对象 |
| 一旧行拆为多个对象 | 联系地址、配方版本、采用阶段等各自保存明确事实 | 可以在不同新对象记录同一旧来源身份，父子关系由新外键维护 |
| 旧代码关系变新外键 | 通过确定的来源键映射到新 ID | 没有完整键的关系不按同色号、名称或最后一条记录猜联 |
| 旧参数横向槽位 | `JobProcess` 的 01～30 槽位按参数行归一化 | 槽位及节点来源完整保留，实际值不能冒充已确定轮次的报工 |
| float/real 改精确业务量 | 使用明确的 Decimal 定义，并保留原浮点值归档 | 实际导入前核对量程和舍入；不能称这种转换为任意浮点无损转换 |
| 数量单位或计算口径改变 | 基本库存量、辅助量、计划量、实测量分别保存，数量换算及计算快照保留需要的扩展精度 | 按已经明确的单位换算，不从旧单位全空字段自动补 kg |
| 新工作流状态 | 沿用当前明确的新枚举，旧整数码逐表映射 | 未确认的旧码不直接变成新系统可执行状态；旧空值不按新建草稿默认覆盖 |
| 干料百分数与 g/L | 新业务显式选择干料质量百分比或浴液浓度，并填写计算基准 | 旧 0/1 只证明百分数/g/L，不能自动证明旧百分数一定采用干料质量基准 |
| 图案 image | `YarnSpecification.pattern_file` 关联现有附件资源 | 提取原图片保存为附件，不改成描述文字 |
| 旧字典变结构化对象 | 单位、仓库、工作中心、包装、标签等使用各自模型 | 字典 NumValue 不能统一解释为 kg；字段值与命名空间一起解释 |
| 包装净重 | 保留明确的扣皮重或固定单粒质量方法与采用结果 | 不通过物料编码位置决定公式，未核实附加重量不加进净重 |
| 旧累计及库存余额 | 通过已生效来源和流水形成查询结果，余额由库存服务维护 | 保留旧结果供对账，不能把累计量和来源量重复入账 |
| 负数及重复条码 | 小数保留，负记录按真实更正/逆向来源处理，条码结合完整来源核对 | 不截整数、不取绝对值、不仅凭条码合并不同记录 |
| 配置冲突或含义未明 | 在对照表保留全部候选，当前使用明确的新含义与生成动作 | 未核实的旧值保留来源档，不写入不适用字段，不设置隐藏默认 |

没有独立旧物理列的 408 个专属字段均逐项列出当前定义和生成/赋值理由，不能标成旧字段的直接复制。这包括新关系、版本、快照、动作时间和单据控制字段。

旧表的 3,712 项字段仍按实际去向区分直接/归一化映射、计算、公共审计、内部键和状态、旧来源保留及财务排除。**“旧来源保留”表示当前没有独立可写新字段，不能算作已实现复刻。** 本次合理安排是保留原始字段和来源，供旧系统只读查询及后续对应业务还原；其字段设置已完整列入逐项对照，能够核实的业务字段在对应功能接入时继续按旧定义落实，不静默丢弃。

## 5. 全部模型的“旧系统id”

已在公共抽象模型 `ErpModel` 增加：

```python
legacy_id = models.TextField("旧系统id", blank=True, null=True)
```

98 个业务模型各有一个真实 `legacy_id` 数据库列，主表、明细、关联表、版本、流水、余额和打印记录均包含。当前账号、菜单、权限等平台模型继续复用，不属于这批 ERP 模型修订。

使用 TextField 是因为旧 ERP 同时存在字符串代码、复合键以及多个来源表；整数 ID 无法完整表达。字段不替代新 `id`，也不承担新外键。

### 5.1 导入约定

字段保存固定结构的 JSON 文本，包含 `schema`、`table`、`key`。主键列名按当前原库，值转为保留实际代码表示的字符串。导入时使用固定序列化格式，示例：

```json
{"key":{"CustomerID":"000012"},"schema":"dye","table":"p_Customer"}
```

```json
{"key":{"ProcessNo":"03","SheetSeries":"0001"},"schema":"dye","table":"JobProcess"}
```

上述数值仅为格式示例。序列化约定为 `json.dumps(identity, ensure_ascii=False, sort_keys=True, separators=(",", ":"))`；不可删除前导零或实际源文本空白。

- `JobSheet` 使用 `SheetSeries`；`SheetNo` 是业务号，不能代替它。
- `JobProcess` 使用 `SheetSeries + ProcessNo`。
- `DyeRecipeDetail`、`StuffWeightDetail` 使用 `SheetSeries + PhaseNo + StuffNo`。
- `RecordYield` 使用 `JobSheetNo + CheckNo + RollNo + Guid`；条码不能代替完整主键。
- `p_FieldValid` 使用 `FieldType + Code`，不能只写 Code。
- 报价及确价同时保存真实物理表名与键，避免别名对调或同号造成错误对比。

### 5.2 空值、重复和衍生对象

新建业务、没有旧对应记录的对象保持 NULL，不编造旧 ID。由多个旧记录归并形成的新路线、缸批、余额等，若没有单一真实旧对象也保持 NULL，完整多对一来源由导入映射清单维护；不能随意取第一条旧行作身份。

旧一行拆成多个新对象时允许重复来源身份，因此 `legacy_id` 不设全局或单模型唯一约束。导入去重需要按明确来源映射和拆分规则完成，不能只做字段全局唯一。

当前所有旧主键候选已经列入逐项对照；候选表不是自动选定来源，实际导入按对象归属确定。只有 UI 复合键或程序关系的对象，先核实真正唯一身份；不使用行号、随机 UUID 或显示条码代替原身份。

此字段当前用于 ORM 和后续导入。后续页面只读展示，并按表名和各键分量展示可读信息；本次没有实现导入程序或对比页面。
